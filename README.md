# sre-incident-evidence-kit

**Multi-source incident evidence timeline + root-cause scoring eval — in pure Python stdlib, no network, no connectors.**

When an incident fires, the loudest alert and the most recent deploy are the easiest suspects — and often the wrong ones. This kit tests a different habit: merge every source into one timeline, score each *given* candidate cause by the evidence that supports **and contradicts** it, and cite the exact evidence IDs behind the ranking.

> Inspiration: the current wave of SRE agents that investigate incidents across observability tools. This is an original, offline build — no MCP servers, no Grafana/Datadog/PagerDuty/AWS connectors, no live data.

## What it proves

- **Analytics + reliability engineering:** evidence fusion across 4 source types, transparent scoring, and a golden eval with a planted ground truth — not a demo that only shows the happy path.
- **Honest evaluation:** a deliberately naive heuristic baseline is measured on the same incidents, so the scorer has to *beat* something, not just look plausible.
- **Red-herring discipline:** several incidents plant a guilty-looking deploy or alert that timing evidence exonerates, and the scorer must cite that contradicting evidence.

## How it works

1. **Incident bundles** (`data/incidents/*.json`, 7 synthetic incidents). Each bundle has four source types — `logs`, `metrics` (series summaries), `alerts`, `deploys` — a planted `ground_truth_cause_id`, and a **given** list of `candidate_causes` (no hypothesis generation; candidates are input, by design).
2. **Timeline** (`timeline.py`) merges all sources into one time-ordered evidence list.
3. **Scorer** (`scorer.py`) scores each candidate: `+weight` per supporting evidence item, `−weight` per contradicting item (decisive items weigh 2, others 1), and records the specific evidence IDs on both sides.
4. **Baseline** (`baseline.py`) is the naive heuristic: latest deploy within 15 minutes of incident start, otherwise the loudest (highest-severity) alert's implied cause.
5. **Evals** (`evals.py` / `run_evals.py`) report top-1 and top-3 root-cause accuracy vs ground truth, evidence completeness (fraction of planted decisive evidence items surfaced in the scorer's citations), and the baseline contrast.

### Red-herring spotlight — inc-001

A deploy lands exactly at incident start (10:00). The baseline picks it. The scorer does not: metrics `inc001-met-01` / `inc001-met-02` show the DB connection pool saturated at 09:40–09:45, **20 minutes before the deploy**, so those items are cited as `contradicted_by` for `deploy_regression`, and `db_pool_exhaustion` wins.

## Honest limits

- **Synthetic and pre-labelled:** evidence items carry explicit `supports` / `contradicts` annotations, so 1.00 is *expected* on this seed set — it validates the timeline/scoring/citation plumbing and the red-herring logic, not real-world diagnosis. A production version would need an extraction layer that infers support/contradiction from raw logs and series, and that layer would score lower.
- **Completeness = 1.00 by construction here:** the scorer reads the whole timeline, so the metric mainly guards against decisive evidence being silently dropped or uncited as the code evolves.
- **Candidates are given,** not generated. No MCP or vendor connectors, no live telemetry, no LLM calls, no network.
- Small seed set (7 incidents); treat the baseline gap as a demonstration of the failure mode, not a benchmark claim.

## Run it

```bash
python3 demo.py            # score all incidents + red-herring spotlight
python3 run_evals.py       # writes eval_report.json and prints headline metrics
python3 -m unittest discover -s tests -v   # 12 tests, stdlib unittest
python3 -m sre_incident_evidence_kit.cli   # module CLI (optional --incident <path>)
```

No dependencies beyond Python 3.10+ standard library. All data is synthetic; plug in your own incident bundles in the same JSON shape to eval on your own cases.

## Layout

```
sre_incident_evidence_kit/  loader, timeline, scorer, baseline, evals, cli
data/incidents/             7 seeded bundles (4 source types each)
tests/test_kit.py           unittest suite (12 tests)
demo.py  run_evals.py       demo + eval entry points
eval_report.json            generated by run_evals.py (git-ignored)
```
